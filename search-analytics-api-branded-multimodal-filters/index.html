Search Analytics API : données de marque, multimodales et multi-pays

Ce que l'annonce du 16 novembre 2026 change pour une boutique qui extrait ses données de la Search Console.

Depuis le 16 novembre 2026, l'API Search Analytics renvoie trois données déjà présentes dans le rapport Performances : les requêtes de marque, les recherches multimodales (Google Lens, Cercle pour rechercher, envois d'images) et les filtres sur plusieurs pays et appareils. Une boutique qui ne lit pas l'API n'a rien à faire cette semaine. Une agence ou un marchand qui automatise ses rapports doit en revanche vérifier trois points avant de comparer deux périodes.

1. Ce qui a été annoncé

Google a publié le 16 novembre 2026, sur le blog Search Central, une annonce de l'équipe Search Console. Elle indique que trois options ajoutées au rapport Performances au cours de l'année précédente arrivent dans l'API : le filtre des requêtes de marque, le rapport de recherche multimodale sur le web et les filtres multi-pays et multi-appareils (billet Search Central, 16/11/2026).

La référence de l'API précise les trois ajouts (référence de la méthode query, lue le 18/11/2026) :

  • brandedClassification sépare les requêtes en deux valeurs, BRANDED et NON_BRANDED. Seul l'opérateur equals est accepté, et le filtre ne se combine pas avec un filtre query dans la même requête.
  • Le type webMultimodal renvoie les données de Google Lens, de Cercle pour rechercher sur Android et des envois d'images dans la recherche Google. Pour les propriétés dont l'export en masse vers BigQuery est actif, ces données figurent aussi dans BigQuery.
  • filterLists permet de filtrer, dans une seule requête, plusieurs pays (codes ISO 3166-1 alpha-3, comme FRA ou BEL) ou plusieurs appareils (DESKTOP, MOBILE, TABLET). Un même champ ne peut pas figurer à la fois dans filters et dans filterLists.

Les données de marque ont une date de départ : le 21 février 2026. Elles ne sont disponibles que pour les propriétés de niveau supérieur qui ont assez de requêtes et d'impressions. Le billet dit la même chose autrement : pour les autres propriétés, la réponse ne contient aucune ligne.

2. Ce que cela change pour une boutique PrestaShop

Le changement touche d'abord le reporting, pas le site. Aucun réglage de la boutique ne modifie ces données. Trois cas se présentent.

Une boutique qui consulte seulement l'interface. Rien à modifier. Les fonctions sont annoncées pour le rapport Performances depuis l'année précédente ; leurs libellés exacts dans l'interface n'ont pas été vérifiés pour cet article.

Une boutique dont le nom est une requête fréquente. Sans filtre, la part de marque et la part hors marque se mélangent. Avec brandedClassification, un script ou un tableau de bord peut afficher les deux séparément, sans maintenir une liste de mots-clés en expression régulière. La part hors marque est celle sur laquelle le contenu des fiches et des catégories agit le plus directement.

Une boutique qui vend dans plusieurs pays. Au lieu d'une requête par pays, un seul appel peut regrouper la France (FRA), la Belgique (BEL) et la Suisse (CHE), ou les appareils MOBILE et TABLET. Le code pays doit être en trois lettres : « FR » n’est pas le format attendu.

Ce n'est pas la même donnée que le trafic web. Le type webMultimodal est une valeur distincte du type web : un total qui additionne les deux mélange deux populations de recherche.

3. Apport original : trois corps de requête contrôlés contre la référence

Pour vérifier la lecture de la référence, trois corps de requête ont été écrits en local, puis contrôlés par un script : noms de champs présents dans la référence lue le 18/11/2026, valeurs acceptées, dates, et règles de combinaison. Le script n'envoie rien à Google et n'utilise aucun identifiant.

UsageChamps utilisésRésultat du contrôle
Part de marque et hors marque, par jourdimensions: ["date"], filtre brandedClassification = NON_BRANDEDvalide
Pages reçues en recherche multimodaletype: "webMultimodal", dimensions: ["page"]valide
Trois pays et deux appareils en une requêtefilterLists sur country (FRA, BEL, CHE) et device (MOBILE, TABLET)valide

Quatre corps volontairement fautifs ont été refusés comme attendu : un opérateur contains sur la marque, une marque combinée à un filtre query, un code pays à deux lettres, et une même dimension dans filters et filterLists. Le script compte 13 contrôles, avec 0 échec (sortie conservée dans preuves/2026-11-18/test/sortie-test-api-requetes.txt).

Ce test valide la forme des requêtes. Il ne dit rien des données renvoyées par Google.

Lecture de consultant. Le point utile de cette annonce est la séparation de la marque, plus que le multimodal. Une part de marque élevée reflète surtout la notoriété du nom, pas le travail sur les fiches. Mon conseil : suivre la part hors marque par famille d'URL (fiches, catégories, pages CMS) et ne lire la part de marque qu'à côté, comme contexte. Sur le multimodal, l'annonce ne dit pas comment les images sont associées aux pages. L'API permet de lister les pages qui reçoivent ces impressions : c'est une liste à lire, pas la preuve qu'une photo produit fait venir du trafic. Hypothèse à vérifier sur vos propres données : les pages qui reçoivent des impressions multimodales sont-elles surtout des fiches à forte identité visuelle ? Un export permettra de le voir, pas une lecture de l’interface.

Que vérifier cette semaine

  1. Si vous avez déjà un export ou un tableau de bord : relevez la date de départ de vos séries de marque. Elles commencent le 21 février 2026 ; ne comparez pas une année pleine avant cette date.
  2. Testez l'éligibilité de la propriété avec une requête brandedClassification sur une période récente, avec vos propres identifiants. Une réponse vide signifie que la propriété n'est pas éligible ou que son volume est insuffisant (annonce et référence).
  3. Vérifiez le type de propriété (domaine ou préfixe d'URL) dans la Search Console avant de promettre une part de marque à un client. La référence parle de propriétés « de niveau supérieur » sans dire en toutes lettres le cas du préfixe d'URL.
  4. Remplacez les listes de pays (une requête par pays, ou des expressions régulières sur le nom de domaine) par un seul filterLists avec des codes à trois lettres.
  5. Si l'export BigQuery est actif, cherchez les lignes webMultimodal dans la table d'export et ne les additionnez jamais aux lignes web.

Limites

  • L'annonce décrit des fonctions. Elle ne mesure aucun effet sur le classement ni sur les clics.
  • Le seuil d'éligibilité (« volume suffisant ») n'est pas chiffré par Google dans les textes lus.
  • Les libellés de l'interface n'ont pas été vérifiés. Le test porte sur la référence, pas sur une vraie propriété ni sur une vraie réponse de l'API.
  • Les données multimodales sont décrites par Google comme une catégorie de recherche. Leur association aux pages produit n'est pas documentée.
